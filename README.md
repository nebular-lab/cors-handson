# CORS 勉強会デモ：なぜブラウザは他サイトの情報を読ませないのか

書籍「フロントエンド開発のためのセキュリティ入門」第4章（同一オリジンポリシーと CORS）を、**攻撃画面のボタンを押すだけ**で体験する15分発表用のデモです。

## 画面（すべて同じ `node server.js` で動く）

| 役割 | URL | 中身 |
|---|---|---|
| 🏠 正規サイト | `http://site.example:3000/mypage.html` | ログイン中ユーザーの個人情報。API は `/api/user` |
| 🤝 連携サービス | `http://partner.site.example:3000/partner.html` | 正当に API を使いたい自社の別サイト。正規サイトと同じドメイン（site.example）のサブドメイン（X-Token 付きで取得） |
| 😈 罠サイト | `http://attacker.example:3000/trap.html` | 正規サイトのマイページを iframe で表示し、攻撃1〜4のボタンで個人情報を盗もうとする |

罠サイトの攻撃：

| ボタン | やっていること | 本の該当箇所 |
|---|---|---|
| 攻撃1 | iframe の中の DOM を直接読む | 4.1・4.2.2・4.3.2 |
| 攻撃2 | `fetch` で API を叩く（単純リクエスト） | 4.4.2 |
| 攻撃3 | `X-Token` ヘッダ付きで API を叩く（プリフライトが必要） | 4.4.3 |
| 攻撃4 | `mode: "no-cors"` で、`X-Token` ヘッダ付きの API を叩く | 4.4.5 |

## CORS の設定なし／あり（git のブランチで切り替える）

CORS の設定は `cors.js` に書いてあり、切り替えると**このファイルだけ**が変わります。

| ブランチ | CORS の設定 | 本のリスト |
|---|---|---|
| `main` | なし | ― |
| `cors-on` | あり：許可リスト（`partner.site.example:3000` と `site.example:3000`）のオリジンだけ許可 | 4-23 |

切り替え方：

```bash
git switch cors-on
```

```bash
git switch main
```

- `npm start` は `node --watch` で動いているので、`cors.js` が変わるとサーバーが自動で再起動します。ターミナルに `===== CORSの設定あり：… =====` と出れば切り替わっています。
- 追加した設定は `git diff main cors-on -- cors.js` で見せられます。

## セットアップ

1. hosts に3行追加する（sudo が必要）
   ```bash
   echo "127.0.0.1 site.example" | sudo tee -a /etc/hosts
   echo "127.0.0.1 partner.site.example" | sudo tee -a /etc/hosts
   echo "127.0.0.1 attacker.example" | sudo tee -a /etc/hosts
   ```
2. クローンして、CORS の設定なし（main）で起動する
   ```bash
   git clone https://github.com/nebular-lab/cors-handson.git
   cd cors-handson
   npm install
   npm start
   ```

API に届いたリクエストは、ターミナルに1行ずつ表示されます。

```
[10:00:00] GET     /api/user  Origin: http://attacker.example:3000  → Allow-Origin: なし  （X-Token: なし）
[10:00:05] OPTIONS /api/user  Origin: http://attacker.example:3000  → Allow-Origin: なし  （要求ヘッダ: x-token → Allow-Headers: なし）
```

## 期待される結果

| CORS の設定 | 連携サービス | 攻撃1 | 攻撃2 | 攻撃3 | 攻撃4 | ターミナルのログ（罠サイトからのリクエスト） |
|---|---|---|---|---|---|---|
| なし（main） | ❌ | 🛡 | 🛡 | 🛡 | 🛡 | 攻撃2：**GET が届いている**／攻撃3：**OPTIONS だけ**／攻撃4：GET が届くが **X-Token なし** |
| あり：許可リスト（cors-on） | ✅ | 🛡 | 🛡 | 🛡 | 🛡 | Allow-Origin が「なし」 |

攻撃1は、CORS の設定に関係なく**ずっと 🛡** です（iframe の DOM の読み取りは CORS では許可されない）。攻撃4も**ずっと 🛡** です（no-cors のレスポンスは、サーバーが何を返しても中身が見えない）。

## 発表の進め方（15分）

### 画面の配置
- 左：ブラウザ。罠サイト（DevTools を開いておく）と連携サービスをタブで切り替える
- 右：ターミナル（`npm start` のログ）。設定の切り替えもここで `git switch` する
- Network タブの「Preserve log」をオンにしておく
- 設定を切り替えたら、数秒待ってからボタンを押す（プリフライトの結果がブラウザにキャッシュされるため）

### タイムテーブル

### 説明で伝えること
- **同一オリジンポリシー**：表示はできても、JavaScript からは読めない。
- **単純リクエスト**：確認なしで送られ、サーバーで処理されたあとに、ブラウザがレスポンスを捨てる。「CORS エラー＝サーバーでは何も起きていない」とは限らない。
- **プリフライト**：独自のヘッダや PUT・DELETE では先に OPTIONS で確認し、許可がなければ本番を送らない。
- **許可リスト**：入れるのは信用できるオリジンだけ。そのサイトに XSS があれば、そこから API を読まれる。
- **no-cors**：エラーが消えるだけで、レスポンスは opaque になり読めない。単純リクエストにならないものは、送らない（PUT など → TypeError）か、はみ出すヘッダを黙って捨てて送る（X-Token など）。プリフライトを避ける手段にはならない。

### デモ1：iframe の中を読む（設定なし）
- 罠サイトを開く。「当選しました！」の画面の中に、正規サイトのマイページが表示されている。
- 攻撃1 → 🛡 `SecurityError`。DevTools の **Elements** を見ると、iframe の中身は表示されている。

### デモ2：API を呼ぶ（設定なし）
1. 攻撃2 → 🛡 `Failed to fetch`。ターミナルのログには **`GET` が届いている**（Allow-Origin: なし）。
2. 攻撃3 → 🛡 `Failed to fetch`。ログには **`OPTIONS` だけ**（要求ヘッダは `x-token`）。DevTools の Network で `preflight` の行も見せる。
3. 連携サービスで「取得する」 → ❌（自社の正当なサービスまで止まる）

言いたいこと：画面のエラーは同じでも、サーバーのログを見ると説明のシーケンス図のとおりになっている。

### デモ3：no-cors で呼ぶ（設定なし）
1. 攻撃4 → 🛡。**エラーは出ない**が、`res.type` は `opaque`、`res.status` は 0、本文は空。
2. ターミナルのログ：**GET が届いている**が、`X-Token: なし`（no-cors では独自のヘッダが捨てられる）。プリフライトも起きていない。

言いたいこと：no-cors はエラーを消すだけで、データは読めない。プリフライトを避けて独自のヘッダを届ける方法にもならない。

### デモ4：許可リストで許可する（設定なし → あり）
1. `git switch cors-on`。`git diff main cors-on -- cors.js` で `allowList` を見せる。
2. 連携サービス → ✅（ログで、返事に Allow-Origin が付いている）
3. 罠サイトの攻撃1〜4 → **すべて 🛡**（罠サイトへの返事は `Allow-Origin: なし`）

### まとめ（3行。最初のゴールと対応）
1. ブラウザは、別のオリジンのデータを **JavaScript から読ませない**（同一オリジンポリシー）。
2. CORS エラーを出しているのは**ブラウザ**。**単純リクエストは届いて処理される**。プリフライトが必要なものは、許可がなければ**本番が送られない**。
3. 読み取りの許可は**サーバー**が CORS ヘッダで出す。no-cors ではデータは読めない。許可するのは信用できるオリジンだけ。

時間が余ったら：Cookie 付きのリクエストでは `*` が使えないこと（4.4.4）に1行だけ触れる。

## 準備中にハマったこと（話のネタにもできる）

**1. レスポンスのキャッシュ**
`*` で許可する設定から許可リストに切り替えても、罠サイトの攻撃2が「😱 盗まれた」のままになった。サーバーが ETag で `304 Not Modified` を返し、ブラウザが前の設定のときの `Allow-Origin: *` 付きのレスポンスを使い回していたのが原因。このデモでは、`/api` を `Cache-Control: no-store` にして ETag も無効にしている。

**2. プリフライトのキャッシュ**
CORS の設定を数秒以内に素早く切り替えると、攻撃3でプリフライト（OPTIONS）が送られず、いきなり GET がログに出ることがある。ブラウザがプリフライトの結果をキャッシュしているため。`Access-Control-Max-Age` を指定しない場合も、Chrome は短時間（数秒）キャッシュする。結果は 🛡 のまま（GET のレスポンスに Allow-Origin がないので捨てられる）だが、ログの見え方が変わる。切り替えたあとは少し待ってからボタンを押すとよい（4.4.3 の `Access-Control-Max-Age` の実例として紹介もできる）。
